6 三個值得展開講的設計Three design calls worth unpacking

不在這三個點上花心思，東西做出來就只是「另一個花費報表」。Skip these three and what you build is just "another spend report."

6.1 為什麼丟掉 hook，改 scan transcripts？Why drop the hook and scan transcripts instead?

之前是 Stop hook 寫 session_metrics.csv，但 hook 只在 .claude/settings.json 有配置的 repo 跑。
結果 vault / Desktop / subagent / 個人 project 的 session 全部漏掉。Used to be a Stop hook writing session_metrics.csv, but hooks only fire in repos with .claude/settings.json configured.
Sessions from vault / Desktop / subagents / personal projects all got dropped.

直接讀 transcripts → 0 設定、覆蓋所有 cwd、不會跟漏 1h cache 計價這種 hook bug。Read transcripts directly → zero setup, every cwd covered, no more hook bugs like missing 1h cache pricing.
6.2 為什麼 monthly 不重新從 .jsonl 算錢？Why doesn't monthly recompute cost from .jsonl?

月度數字 = Work Items DB SUM 出來。Daily 是事實層，Monthly 是聚合層，永遠不會兩邊算出不一樣的數字（避免「我每天看的是 $200，月底結算變 $214」這種事）。Monthly numbers = SUM of the Work Items DB. Daily is the facts layer, monthly is the aggregation layer — the two can never disagree (no more "I saw $200 daily but the month closed at $214").

parse.py 只負責補 Work Items 沒存的 行為指標：短回覆率、Opus 佔比、session 長度分佈。parse.py only fills in the behavioral metrics Work Items doesn't store: short-reply rate, Opus share, session-length distribution.

Single Source of Truth — Daily 跟 Monthly 看同一張表，永遠對得起來。Single Source of Truth — daily and monthly read the same table, always reconcile.
6.3 為什麼 ticket 還要打 Linear API 驗一次？Why double-check tickets against the Linear API?

parse.py 用 regex [A-Z]{2,}-\d+ 抓 ticket ID，但會誤抓：parse.py uses the regex [A-Z]{2,}-\d+ to pull ticket IDs, but it false-positives on:

• 別人 paste 的 archive 列表（[已合併] CAF-XXX）
• dispatcher 列出來的 routed tickets（自己沒做）
• /list-worktrees / /remove-worktree 列出來的票
• Notion 頁面內容裡有人提過的 ticket ID • archive lists someone pasted in ([merged] CAF-XXX)
• routed tickets the dispatcher listed (not actually mine)
• tickets surfaced by /list-worktrees / /remove-worktree
• ticket IDs mentioned inside Notion page content

所以對於 regex 抓到、但 cwd / branch 又沒驗證到的 ticket，會額外打 Linear API 確認是不是真的存在。不存在就清掉，避免假 ticket 進 Notion。So for tickets the regex catches but cwd / branch can't confirm, hit the Linear API to verify they really exist. If not, drop them — no phantom tickets in Notion.

資料品質 > 資料數量。寧可少抓，不要錯抓。Data quality > data quantity. Rather miss one than miscount one.

8 Takeaway

  1. 0 設定的觀測 — 直接讀 Claude Code 自己寫的 transcripts，不靠任何 hook。Zero-setup observability — read the transcripts Claude Code already writes; no hooks required.
  2. Daily 是事實，Monthly 是行為 — Daily 記每張票每段時間；Monthly 從中聚合 + 加行為層分析。Daily is facts, monthly is behavior — daily logs every ticket and time window; monthly aggregates from that plus behavioral analysis on top.
  3. SSOT — 月度永遠 SUM Daily 寫進 Notion 的數字，避免雙寫對不起來。SSOT — monthly always SUMs what daily already wrote into Notion; no two writes that disagree.
  4. TOP 5 不是排行榜 — 是「具體事蹟 + 數據 + 實例 + 為什麼/怎麼改」的可行動觀察。TOP 5 isn't a leaderboard — it's actionable observation: concrete event + numbers + example + why / how to change.
  5. 資料品質 > 資料數量 — 寧可打一次 Linear API，也不要讓假 ticket 污染 dashboard。Data quality > data quantity — pay one Linear API call rather than let phantom tickets pollute the dashboard.
