3 核心概念Core concepts

四個關鍵詞撐起整套設計。Four keywords carry the whole design.

🌳

One worktree per ticket

路徑 = ../<TICKET-ID>。Dispatcher 才能 inline 算出 worktree path、不用查表。Path = ../<TICKET-ID>. Dispatcher computes the worktree path inline — no lookup needed.

🔌

Platform-aware

Flutter 跑 flutter pub get、iOS 跑 pod install、Android 留給 IDE sync —— 由 platform profile 決定。Flutter runs flutter pub get, iOS runs pod install, Android defers to IDE sync — driven by the platform profile.

🧭

狀態靠 join，不靠記State by join, not by storage

不存任何 worktree 本地 state；要看「完成了嗎」就現拉 PR + ticket 即時 join。No local worktree state stored anywhere; to check "is it done?" we fetch PR + ticket and join on the fly.

🛡️

Human gate on destruction

--auto 再聰明也只是推薦，最終 AskUserQuestion 一定要過。No matter how smart --auto gets, it only recommends — the final AskUserQuestion always gates.

5 三個 skill 各自的重點What each skill nails

每個都只做一件事，但那件事做得很到位。Each does one thing, but that one thing dialed all the way in.

5.1 /add-worktree — 一條指令把環境準備好one command, environment ready

它不只是 git worktree add 的 wrapper。讀 .gogox-claude.yaml 找出 platform，呼叫對應的 platform profile（flutter.yaml / ios.yaml / ...），自動跑該專案的 deps_install 指令，再印出該專案的 ide_open_hint。Not just a git worktree add wrapper. Reads .gogox-claude.yaml to find the platform, calls the matching platform profile (flutter.yaml / ios.yaml / ...), runs the project's deps_install command, prints the project's ide_open_hint.

路徑固定是 ../<TICKET-ID> —— 這不是美觀問題，是協議。Dispatcher、/list-worktrees、/remove-worktree 都靠這個 convention 倒推路徑，不必查表。Path is locked to ../<TICKET-ID> — not aesthetics, this is a protocol. Dispatcher, /list-worktrees, and /remove-worktree all rely on this convention to derive paths without a lookup.

5.2 /list-worktrees — 把分散資訊 join 在一張表scattered signals joined into one table

對每個 worktree 平行收集：branch、ticket ID、Linear/Jira 狀態、PR URL + state + review decision、ahead/behind trunk、dirty 與否、最後 commit 時間、目前 cwd 是不是在這個 worktree。For every worktree, collect in parallel: branch, ticket ID, Linear/Jira status, PR URL + state + review decision, ahead/behind trunk, dirty flag, last commit time, whether the current cwd is this worktree.

關鍵是平行收集。N 個 worktree 各自跑 git + gh + Linear，全部 fan-out 同一個 batch，總時間 ≈ 單一查詢時間。The key is parallel collection. N worktrees each run git + gh + Linear, fanned out in one batch — total time ≈ one query's time.

5.3 /remove-worktree --auto — 整套的點睛之筆the finishing stroke

這是最值得單獨講的一個。它不是「刪所有 worktree」也不是「刪 N 天以上的 worktree」。它做了一件更難的事：The one most worth highlighting. It is not "delete all worktrees" or "delete worktrees older than N days". It does something harder:

→ Sweep 所有 secondary worktrees
→ 對每張票，同時問 GitHub「PR merged 沒？」+ 問 ticket tracker「狀態是不是 Ready for QA？」
→ 兩者都 yes 且 working tree clean，才放進 RECOMMENDED
→ 任何一個 signal 是 unknown？一律降級 KEEP（fail-safe）
→ 最後印兩張表（RECOMMENDED + KEEP）讓人看完才能按下去 → Sweep all secondary worktrees
→ For each ticket, concurrently ask GitHub "PR merged?" and the ticket tracker "status = Ready for QA?"
→ Both yes AND working tree clean → RECOMMENDED
→ Any signal unknown? Demote to KEEP (fail-safe)
→ Print two tables (RECOMMENDED + KEEP) and only act after a human reads them

6 值得展開講的設計Design choices worth unpacking

幾個看似小、其實扛了很多重量的決定。A few decisions that look small but carry a lot of weight.

6.1 為什麼是 worktree 不是切 branch？Why worktrees, not branch-switching?

切 branch 共用同一個 working directory：build artifacts、IDE index、hot reload state 全部共用，切過去切回來就 invalid 一次。Worktree 每個都是獨立資料夾，build cache 各活各的、IDE 各開各的。對 dispatcher 來說更關鍵 —— N 個 background agent 不能共用一個 cwd。Branch-switching shares one working directory: build artifacts, IDE index, hot reload state — all shared, all invalidated on every flip. Worktrees are independent folders, so each has its own build cache, its own IDE window. More critical for the dispatcher — N background agents can't share one cwd.

Worktree 是把 git 的線性歷史，攤平成可平行的工作空間。A worktree flattens git's linear history into parallel workspaces.
6.2 路徑命名 ../<TICKET-ID> 為什麼是協議Why ../<TICKET-ID> is a protocol

Dispatcher 在 spawn agent 之前不會去查「這張票的 worktree 在哪」—— 它就算出來。basename(cwd)/../CAF-272 一行 shell 就拿到 absolute path。如果路徑命名是隨意的，dispatcher 就要先掃一遍 git worktree list、配對 branch、再撈 ticket ID，多走兩三步。Before spawning an agent, the dispatcher doesn't look up "where is this ticket's worktree" — it computes it. basename(cwd)/../CAF-272, one line of shell, absolute path in hand. If naming were arbitrary, the dispatcher would have to scan git worktree list, match branches, fetch ticket IDs — two or three extra steps.

當下游有多個工具要依賴你的輸出，命名 convention 就不是品味問題，是 contract。Once multiple downstream tools depend on your output, naming is no longer taste — it's a contract.
6.3 Platform-aware 為什麼放在 add，不放在 list / removeWhy platform-aware lives in add, not list/remove

建立 worktree 才需要知道「這是 Flutter 還是 iOS」—— 要不要跑 pub get、要不要 pod install。List 和 remove 都是 platform-agnostic：列 git 狀態、刪 git worktree，不關心你是哪個 stack。職責切得乾淨，三個 skill 才能各自迭代。Only creation needs to know "is this Flutter or iOS?" — whether to run pub get or pod install. List and remove are platform-agnostic: list git state, delete a git worktree, doesn't care about your stack. Clean separation of duties — that's what lets the three skills iterate independently.

「platform-aware」是成本，不是美德。只在真的需要的地方付。"Platform-aware" is a cost, not a virtue. Pay it only where you must.
6.4 --auto 模式為什麼一定要 human gateWhy --auto must keep a human gate

它是破壞性操作，而且依賴的「完成信號」是兩個外部系統的 join（GitHub PR + ticket tracker）。任何一個系統 API 出小錯、任何一個 ticket 被改了 workflow name、任何一個 PR merge 後又被 revert —— 都可能誤判。It's a destructive operation, and the "done signal" it relies on is a join across two external systems (GitHub PR + ticket tracker). One API hiccup, one renamed workflow state, one PR merged-then-reverted — any of these can flip the verdict.

所以 --auto 只負責「把判斷理由攤開給人看」：RECOMMENDED 表附完整 reason，KEEP 表附 first applicable rule，每個 row 都點得進 ticket / PR。人類花 10 秒掃一眼就能否決，這比任何 confidence threshold 都可靠。So --auto's job is to lay out the reasoning for a human: RECOMMENDED rows carry a full reason, KEEP rows carry the first applicable rule, every row links to its ticket / PR. A human scans for 10 seconds and can veto — more reliable than any confidence threshold.

自動化的天花板，是把判斷依據呈現得讓人可以快速否決。The ceiling of automation is making the reasoning visible enough for humans to veto quickly.
6.5 任何 unknown signal 一律降級為 KEEPAny unknown signal → KEEP

PR API 失敗？KEEP。Ticket lookup timeout？KEEP。Branch 找不到 prefix？KEEP。不在資訊不全時做破壞性決定。代價是偶爾要手動清，但比誤刪好太多。PR API failed? KEEP. Ticket lookup timed out? KEEP. Branch prefix unmatched? KEEP. Never make a destructive call on incomplete info. The cost is the occasional manual cleanup — far better than wrongful deletion.

8 Takeaway

如果分享只能記住五件事。If you only remember five things.

  1. 一張票一個 worktree —— 不是 nice-to-have，是 dispatcher 平行作業的前置條件。One ticket, one worktree — not a nice-to-have, but the precondition for the dispatcher's parallelism.
  2. 路徑命名是協議 —— ../<TICKET-ID> 讓下游工具不必查表，直接算出來。Path naming is a protocol — ../<TICKET-ID> lets downstream tools compute, not look up.
  3. Platform-aware 只放在需要的地方 —— 只有 add 關心 stack，list / remove 純 git，三個 skill 各自迭代。Platform-aware only where needed — only add cares about the stack; list / remove are pure git, so the three skills iterate independently.
  4. 狀態靠 join，不靠存 —— 即時 join PR + ticket，不維護任何 worktree 本地 state。State by join, not by storage — join PR + ticket on demand, no local worktree state to maintain.
  5. 破壞性自動化必須留 human gate —— 自動化的價值在「把判斷依據攤開」，不在「自己按下去」。Destructive automation keeps a human gate — automation's value is laying the reasoning out, not pressing the button.
