WHY

為什麼這條 pipeline 長這樣？ Why is the pipeline shaped this way?

三個關鍵設計決策 three core design decisions
01 為什麼要先 detect state A/B/C？ Why detect state A/B/C first?

port 流程做完才到 dev 是常態，但有時人類直接從 ticket 跑 dev（沒 port）。Detect 讓同一個 /dev:ff 在「artifact 從零開始」（A）跟「artifact 已存在從 apply 開始」（B）兩種情況都能跑。tasks.md 的 [x] 計數是判定的 ground truth——純 grep 不靠 LLM。 port → dev is the usual path, but sometimes humans run dev straight from the ticket (no port). Detect lets the same /dev:ff handle both "artifact from zero" (A) and "artifact already exists, start at apply" (B). [x] counts in tasks.md are the ground truth — pure grep, no LLM.

分類是 routing 的前提；路由器和工作站不能合一起。 Classification is a prerequisite for routing; the router and the workstation can't be the same thing.
02 為什麼 align 要在 apply 之前？ Why does align run before apply?

port 的 synth 階段如果引用了不在 Figma receipt 裡的 node ID、或描述了不存在的 design token，bug 會一路帶到 code。Align-subagent 在 apply 開跑前獨立稽核 OpenSpec ⇄ receipt 的一致性，這是 anti-hallucination 的二道防線（spec-lint 是第一道）。 If port's synth stage cites a node ID that isn't in the Figma receipt or describes a design token that doesn't exist, the bug rides straight into code. Align-subagent independently audits OpenSpec ⇄ receipt consistency before apply runs — the second line of anti-hallucination defense (spec-lint is the first).

Figma raw 是 ground truth，spec 只是衍生品。對不上時，信 ground truth。 Figma raw is ground truth; the spec is a derivative. When they disagree, trust ground truth.
03 為什麼 verify-agent 要獨立 spawn？ Why spawn verify-agent in isolation?

Apply agent 看自己的 diff 會自動護短——漏掉 rename 沒清的 stale call site、移除函式但留下引用。獨立 spawn 的 verify-agent 沒有 prior context、不同 model（sonnet vs apply 的 opus）、讀 raw 不讀 receipt，才能抓得到 contract surface 的破口。 An apply agent reviewing its own diff covers for itself — misses stale call sites from incomplete renames, leaves dangling references after removing functions. An independently spawned verify-agent with no prior context, a different model (sonnet vs apply's opus), reading raw not receipt — that's what catches the contract-surface gaps.

同 session 寫 code 又自審等於沒審。乾淨 context 是反幻覺的二保險。 Writing code and self-reviewing in the same session is no review. Clean context is the second insurance against hallucinations.
MODES

--auto vs default · 誰來按 enter？ --auto vs default · who hits enter?

同一條 pipeline 兩種跑法 two ways to run the same pipeline
DEFAULT MODE

👤 人類在鍵盤前 👤 Human at the keyboard

三個 HITL gate 全部會跳：figma 失敗、align CONFLICT、apply 寫完 artifact。人類拒絕，pipeline 就停在那。 All three HITL gates trip: figma failure, align CONFLICT, apply finishes artifact. Human says no, the pipeline stops there.

Apply 在 default 會 spawn dev-agent（opus）跑 /opsx:apply，context 隔離。手動推單張票用這個。 In default, apply spawns dev-agent (opus) to run /opsx:apply with isolated context. Use this when manually driving one ticket.

--AUTO MODE

🤖 給 dispatcher 跑 🤖 For the dispatcher

HITL gate 一律自動通過或變 STOP（沒人答就停在那、等下次 resume）。所有失敗變 abort。 HITL gates auto-pass or turn into STOP (no answer → pause, wait for the next resume). Any failure becomes abort.

Apply 改成 inline 跑——因為 /ggx-dispatcher 已經把 /dev:ff --auto 包在 subagent 裡，再 nest spawn opus 不穩。Dispatcher 平行跑批次票用這個。 Apply runs inline instead — /ggx-dispatcher already wraps /dev:ff --auto in a subagent, and nesting another opus spawn is unstable. Use this when the dispatcher runs tickets in parallel.

關鍵設計KEY DESIGN mode 是 invocation-scoped、progress 是 worktree-scoped mode is invocation-scoped, progress is worktree-scoped

「mode」不會被記住——/dev:ff 每次調用都從這次的 $ARGUMENTS 讀 --auto 旗標。同一個 worktree 上半段 default 跑完，下半段加 --auto 接著跑，完全合法。 "Mode" isn't remembered — every /dev:ff invocation reads the --auto flag from that call's $ARGUMENTS. Run the first half of a worktree in default, then add --auto for the rest — completely fine.

TAKEAWAY

記住這四件事 Remember these four things

分享結束如果只能帶走幾句話 if you only walk away with a few lines
  1. State 存 filesystem，不存 memory——8 個 stage 各有 marker，中斷、重跑、被 dispatcher 接手都行。 State lives on the filesystem, not in memory — each of the 8 stages has its own marker; interrupt, re-run, hand off to the dispatcher, all fine.
  2. HITL gate 預設留三道——default 模式人類把關 figma / detect / apply；dispatcher 用 --auto 就全自動。 Three HITL gates by default — humans guard figma / detect / apply in default mode; the dispatcher uses --auto for full automation.
  3. Align + verify 各自獨立 spawn——是反幻覺的雙保險，apply 看不到自己的盲點，由乾淨 context 的 auditor 抓。 Align + verify are independently spawned — the double insurance against hallucination; apply can't see its own blind spots, so a clean-context auditor catches them.
  4. Walker 從 filesystem 重新推導 stage——infer_dev_stage 每次重新跑，stage 之間沒有 in-memory dependency，所以可以中斷重跑。 The walker re-derives the stage from the filesystem — infer_dev_stage runs fresh every time; no in-memory dependency between stages, so interrupt-and-resume just works.
