把新發現的問題跟舊的 review 留言合成一次修改，審乾淨再等 CI 綠。
預設停在 draft ——「這是人看過的」是人自己按的。Rebase onto base and auto-resolve conflicts, then let a different agent review the diff, fix the fresh findings together with the pre-existing review threads in one combined pass, loop until the review is clean, then wait for CI to go green. It stops at draft by default — 'a human has checked this' is a human's own click.

WHY

為什麼是這個形狀？Why this shape?

🪞

寫的人不審自己The author never audits itself

審的 agent 跟寫 code 的 agent 是分開的，而且它讀的是遠端 PR 的真實 diff，不是「實作者自己寫的摘要」。同一顆腦袋、或看同一份摘要，會犯一樣的錯——這就是 adversarial verification 在真實 pipeline 裡的樣子。The reviewing agent is not the implementing agent, and it reads the real diff on the remote PR, not the implementer's own summary. One brain — or one summary — makes the same mistake twice. This is adversarial verification as it actually appears in a pipeline.

🔁

一輪一個 commitOne commit per round

每一輪把「新發現」跟「舊留言」合成一次修改、一次 push。分成兩段就會留下一個修了一半的 HEAD，下一輪去審那個半成品，然後迴圈就永遠收不乾淨。Each round merges 'fresh findings' and 'old threads' into one fix and one push. Splitting them leaves a half-fixed HEAD for the next round to review, and the loop stops converging.

🚦

draft / ready 是團隊的訊號draft / ready is the team's signal

draft = AI 寫的、還沒人驗過；ready = 有人看過了。既然這個意思是團隊約定的，機器就不該自己把它翻成 ready。--assign 那一下就是簽核。draft = AI-written, not yet verified; ready = a human has checked it. Since that meaning is a team convention, a machine must not flip it on its own. Passing --assign IS the sign-off.

EXIT #3迴圈要有第三個出口A loop needs a third exit

「審乾淨」和「跑到 5 輪」是前兩個出口。第三個是 human-decision：只要有一條意見需要人做產品判斷，就當場停下來、印出人要決定什麼。沒有這個出口，一個 AC 對不上的爭議會被當成程式問題反覆改五輪，然後留下五個沒人想要的 commit。'The review is clean' and 'five rounds spent' are the first two exits. The third is human-decision: the moment a finding needs a product call, stop and print what the human must decide. Without it, an acceptance-criteria disagreement gets treated as a code problem for five rounds and leaves five commits nobody wanted.

會自己說「我卡住了、卡在哪一條」的迴圈，比會跑滿次數的迴圈有用。A loop that can say 'I'm stuck, and here is the rule that stopped me' is worth more than a loop that reliably burns its budget.
PROBE「查不到」跟「確定沒有」要分開'inconclusive' is not 'confirmed absent'

探測 repo 有沒有 @claude 時，清單和 grep 是分兩步做的——因為一個 pipe 的 grep 失敗，「gh api 出錯」跟「確定沒有 claude workflow」會回同一個 exit code。分不開的話，一次網路抖動就會讓所有 repo 都被判成沒有 @claude。查不到就 fail open。The @claude capability probe lists the workflows and greps them in two separate steps, because a single pipe cannot distinguish 'gh api errored' from 'confirmed no claude workflow' — grep exits 1 for both. Conflated, one network blip would judge every repo as having no @claude. Inconclusive fails open.

TAKEAWAY

記住這四件事Remember these four things

  1. 審的人要換一顆腦袋，而且要看原始資料——不同 agent、讀遠端真實 diff，不是讀實作者的摘要。The reviewer needs a different brain and the raw material — a different agent reading the real remote diff, not the implementer's summary.
  2. 出口寫成名字——七種 STOP 各有名字，報告直接說出是哪一關擋的，而不是一句「失敗」。Name the exits — seven STOPs, each named, so the report says which gate stopped it instead of just 'failed'.
  3. 停下來也要記成本——STOP 不代表這一趟免費；只有還沒動工的兩個出口不計。A STOP still costs — stopping does not make the run free; only the two exits that happen before any work skip the metrics.
  4. 最後那一下留給人——這一段是四段裡唯一「人啟動、人收尾」的；機器不自己把 draft 翻成 ready，也永不 merge。Leave the last click to a human — this is the one stage of the four that a human both starts and finishes. The machine never flips draft to ready, and never merges.
