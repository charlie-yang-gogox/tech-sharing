WHY

為什麼是這個形狀？Why this shape?

🎯

判斷外派，選擇留下Farm out judgement, keep selection

票池、過濾、排名都留在 orchestrator——那是算術，量也不大，而且每張票的 tie-break 理由是要進報告的稽核輸出，不能經過一層摘要。分類、prescreen、深入調查才外派，因為那三段是判斷。Pool, filters and ranking stay in the orchestrator — that is arithmetic, the volume is moderate, and each ticket's tie-break reason is required audit output that must not pass through a summarising layer. Classification, pre-screening and the deep pass are farmed out, because those three are judgement.

🧱

一個 agent 只給它一份規則One agent, one rule file

三段判斷各有一個 stage 檔（classify.md / prescreen.md / investigate.md），每個 agent 被指到其中一份，其他什麼都不給。harness 很薄，判斷全在那三個檔案裡——要改行為就改檔案，不用改腳本。Each judgement phase has one stage file (classify.md / prescreen.md / investigate.md) and each agent is pointed at exactly one of them and given nothing else. The harness is thin and every judgement lives in a file — change behaviour by editing the file, not the script.

🚚

長文用路徑回傳Long prose comes back by path

agent 寫出來的 note 是一個檔案，回傳值只有路徑。這不是潔癖——這條傳輸路徑被實測過會把過長的欄位截掉，而被截掉的 note 看起來跟一份「寫得比較短」的 note 一模一樣。An agent's note is a file; the return value carries only its path. Not fastidiousness — that transport has been measured truncating an over-long field, and a truncated note looks exactly like a note that was simply written shorter.

REVERSAL從「懶惰地一張一張看」改成「整批一起篩」From a lazy one-at-a-time walk to screening the whole bound at once

早一版是照排名往下走、一張一張抓描述，抓到湊滿名額就停，並且把這個懶惰走法當成核心設計。它唯一的理由是省主 session 的 context——而 subagent 本來就解決了這件事。所以正確的設計恰好相反：整個上限一次平行篩完，再照排名取前 N 個通過者。wall-clock 從 N 次序列抓取塌成一輪，而「篩完沒有任何一張需要深入調查」本來就是常態（大約四張裡才有一張需要）。An earlier version walked down the ranked list fetching descriptions one at a time, stopped once the slots were full, and called that lazy walk load-bearing. Its ONLY justification was main-session context — which a subagent removes. So the correct design is the opposite: pre-screen the whole bound in parallel, then take the highest-ranked N passers in rank order. Wall-clock collapses from N serial fetches to one round, and a pre-screen that produces no deep pass was always the documented normal case (roughly one candidate in four needs one).

TWO BOUNDS「篩幾張」跟「做幾張」是兩個數字'how many to screen' and 'how many to do' are two different numbers

每一 tick 篩固定的五張候選，通過的裡面才照名額取。把這兩個數字混成一個，就是那條規則存在的原因——名額是三，不代表只該看三張。Each tick pre-screens a fixed five candidates; the slots then take from the passers. Conflating the two numbers is exactly the mistake the rule exists to prevent — three slots does not mean only three candidates deserve a look.

TAKEAWAY

記住這四件事Remember these four things

  1. 兩票分類，兩個 tier——haiku 提案、sonnet 盲審。同一顆模型審自己不會發現自己的盲點。Two votes, two tiers — haiku proposes, sonnet confirms blind. One model checking itself never finds its own blind spot.
  2. barrier 要有理由才存在——這裡的理由是「前 N 個通過者」這個定義本身需要全部的判定。沒有這種理由的階段就不要設 barrier。A barrier needs a reason — here it is that 'the highest-ranked N passers' is undefined until every verdict lands. A stage without such a reason should not have one.
  3. adopt 是四筆寫入的原子操作——半套 adopt 比不 adopt 更糟：票看起來可動，但下游讀不到 lane。Adopt is four writes, atomically — a half-adopt is worse than none: the ticket looks actionable while downstream cannot read its lane.
  4. 被篩掉的票要看得見——每一張排除都印一行理由。掃過但沒提的票，讀起來就像從來不存在。Filtered-out tickets stay visible — every exclusion prints one line with its reason. A ticket that was swept but never mentioned reads as one that never existed.
