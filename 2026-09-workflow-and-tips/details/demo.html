WHY

為什麼是這個形狀？Why this shape?

💸

便宜的先判，貴的最後做Judge cheap, act expensive

整條流程的成本幾乎全在「開裝置 + build + 驅動 app」。所以判斷「這張錄不錄得到」用 diff 就好，不用開機。這就是 generate-and-filter 的實用版：候選是掃出來的，濾網是規則，而濾網放在花錢之前。Almost the whole cost sits in 'open a device, build, drive the app'. So the recordability judgement reads a diff instead of booting anything. That is generate-and-filter in its most practical form: the candidates are found, the rubric filters them, and the filter sits before the spend.

🔌

序列不是設計倒退Serial is not a design regression

形狀還是 fan-out：一張票一個 agent、各自回一份有結構的結果。只是同時在跑的永遠只有一個，因為瓶頸是一台實體裝置。把物理限制寫進 harness，比讓五個 agent 去搶同一台好。The shape is still a fan-out: one agent per ticket, each returning a schema-validated result. Only one runs at a time, because the bottleneck is one physical device. Encoding the physical limit in the harness beats letting five agents fight over it.

🙋

這一段的人工是刻意留的The human gate here is on purpose

拍攝計畫的確認是無條件的，沒有旗標能關。因為「錄錯東西」的代價不是重跑一個 agent，而是整批重排一次共用裝置——這種代價值得一次人工確認。The capture-plan confirmation is unconditional and no flag skips it. Recording the wrong thing does not cost one agent re-run; it costs the whole shared-device pass — and that is worth one human look.

MEASURED濾網太緊，跟濾網太鬆一樣糟Too tight a filter is as bad as too loose

早期一批 12 張 PR 只錄成 1 張，被跳過的裡面有明顯錄得到的。原因不是模型爛，是規則寫得太保守：「靜態截圖看不出差別」「只靠點擊選不到」被當成不可錄。修的是規則，不是模型——現在「要打字」「要下單」都算可錄，因為 staging 上真的驅動得到；只有真的走不到的狀態才留在 SKIP。An early batch of 12 PRs produced one recording, and obviously-recordable PRs were among the skips. Not a model problem — the rubric was too conservative: 'no pixel diff in a static shot' and 'nav-only taps cannot select it' were treated as unrecordable. The fix was to the rubric, not the model — 'needs typing' and 'needs an order' now count as recordable because staging genuinely drives them, and only truly unreachable states stay in SKIP.

錄影是要證明「它會動」。如果規則讓大部分會動的東西都被判成錄不到，那這一段就等於沒有。A recording exists to prove the thing works. If the rubric judges most working things unrecordable, the stage might as well not run.
TAKEAWAY

記住這四件事Remember these four things

  1. 濾網放在花錢之前——讀 diff 判斷，比開裝置便宜兩個數量級。Put the filter before the spend — judging a diff is two orders of magnitude cheaper than booting a device.
  2. 濾得太兇要當成 bug 修——12 張錄到 1 張不是模型問題，是規則問題。Over-filtering is a bug to fix — 1 of 12 was a rubric problem, not a model problem.
  3. 物理限制寫進 harness——一台裝置就寫成序列，不要讓 agent 互搶。會弄髒登入狀態的排最後。Encode the physical limit — one device means serial in the harness, not agents contending. Anything that dirties login state goes last.
  4. 沒發佈就不能報告成 attached——去重是靠留言裡的 sha，謊報成功會讓同一張 PR 被永遠重錄。Never report 'attached' without publishing — dedup keys on the sha in that comment, so a false success re-records the same PR forever.
