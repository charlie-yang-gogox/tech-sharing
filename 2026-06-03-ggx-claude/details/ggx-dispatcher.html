WHY

為什麼是這個形狀？Why this shape?

三個關鍵設計決策Three key design decisions
01 為什麼 4 條 Linear query 而不是 1 條？Why 4 Linear queries instead of 1?

Fresh (Q1/Q3) 是「該開工的票」、Recovery (Q2/Q4) 是「dispatcher 上次中斷的票」，兩種狀態都要 cover。Port 與 Dev 兩條 pipeline 又要分離 routing —— 4 queries 是「角色 × 階段」的最小組合，每筆 result 都帶清楚的 lane 標籤，分派 /port:ff 或 /dev:ff 不用再 re-derive。Fresh (Q1/Q3) covers "tickets ready to start"; Recovery (Q2/Q4) covers "tickets the previous dispatcher dropped mid-flight" — both states need coverage. Port and Dev pipelines need separate routing too — 4 queries is the minimum "role × stage" matrix. Every result carries an unambiguous lane tag, so dispatching /port:ff vs /dev:ff never has to be re-derived downstream.

把 routing 資訊塞在 query 結構裡，下游 dispatcher logic 就不需要再猜這張票是 fresh 還是 recovery、是 port 還是 dev。Encode the routing in the query structure — then downstream dispatcher logic never has to guess fresh vs recovery, port vs dev.
02 為什麼 race-lock 失敗整批回滾？Why does race-lock roll back the whole batch on failure?

Partial lock 是最糟狀態：N 張票被自己 lock 走、background agent 沒 spawn 起來、別人的 dispatcher 撈到 in-flight label 又不會碰。回滾把 fresh-lane 退回 ready-to-*（recovery-lane 保留 in-flight，因為它原本就在等被接手）。Partial lock is the worst state: N tickets locked by us, no background agents actually spawned, and other dispatchers see the in-flight label and won't touch them. The rollback reverts the fresh lane back to ready-to-* (the recovery lane keeps its in-flight label — it was already waiting to be picked up).

All-or-nothing 比 best-effort 安全 —— 系統可以 abort，但不可以「半 lock」。All-or-nothing is safer than best-effort — the system is allowed to abort, but never to "half-lock".
03 為什麼 spawn N agent 一定在 same message？▲ 已被取代Why must N agents spawn in the same message? ▲ superseded

平行的物理條件。不同 message 等於依序 spawn、wall-clock 翻 N 倍。Dispatch table 印完之後不要停下來「讓使用者確認」—— 直接接著 emit N 個 Agent call + 1 個 poller Bash call，全部在同一 assistant turn。It's the physical condition for parallelism. Separate messages mean serial spawn — wall-clock multiplies by N. After printing the dispatch table, do NOT pause to "let the user confirm" — emit N Agent calls + 1 poller Bash call back-to-back, all inside the same assistant turn.

「同一個 message 裡 spawn」是平行的物理條件，不是優化技巧。"Spawn in the same message" is the physical condition for parallelism — not an optimization trick.

▲ 2026-08：這個限制現在不存在了。平行度由 Workflow 腳本決定，不再由 message 邊界決定——所以也不必再擔心「印完 dispatch table 之後停下來就變序列」。留著這一段是因為它解釋了當時為什麼要那樣寫。▲ 2026-08: this constraint is gone. Concurrency is set by the Workflow script, not by a message boundary — so pausing after the dispatch table no longer serialises anything. The block is kept because it explains why the code once looked that way.

記住這四件事Remember these four things

分享結束如果只能帶走幾句話If you only take a few lines away from this talk
  1. Dispatcher 不是 service、是 one-shot command —— session 關了就停，不用 daemon、不用 cron。The dispatcher is not a service — it's a one-shot command — close the session and it stops. No daemon, no cron.
  2. Label 是 state machine —— ready-to-* 進、dispatcher-*-in-flight 中、need-spec-review 出，每個 transition 都 atomic。Labels are the state machine — ready-to-* in, dispatcher-*-in-flight running, need-spec-review out. Every transition is atomic.
  3. 平行度歸腳本管 ▲ —— 2026-06 是「同一個 message spawn」，現在是 Workflow 腳本 fan-out；換來 journal、resume 和 token budget。Concurrency belongs to the script ▲ — in 2026-06 it was same-message spawn; today it is a Workflow-script fan-out, which buys a journal, resume and a token budget.
  4. 可中斷 / 可續跑 —— 上次中斷的票下次自動被 Q2/Q4 接手，狀態存在 Linear label。Interruptible and resumable — last run's dropped tickets get picked up by Q2/Q4 next time. State lives in the Linear label.
