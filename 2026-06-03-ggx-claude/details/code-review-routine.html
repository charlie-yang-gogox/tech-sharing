WHY

為什麼是排程，不是 PR-hook？why scheduled instead of a PR hook?

三個關鍵設計決策three core design decisions
01 為什麼 03:00 HKT 排程，不是每次 push 都跑？why schedule at 03:00 HKT instead of running on every push?

PR push 完通常還會 force-push、補 commit、改 typo。掛在 push trigger 上跑會浪費 review credit、produce 重複 findings——同一個 file:line 被 review 三遍，dev 早上要過濾的雜訊量直接翻倍。03:00 HKT 是所有 dev 都下班後的 quiet point，PR diff 已經穩定，review 一次涵蓋整輪。A PR push is almost always followed by a force-push, a fixup commit, a typo fix. Hooking review onto push burns review credits and produces duplicate findings — the same file:line gets reviewed three times, doubling the noise the dev has to filter the next morning. 03:00 HKT is the quiet point after every dev has clocked out: the PR diff has settled and one review pass covers the whole round.

Trigger 不挑時機，就是用噪音換 coverage。挑對時機，才換到真 baseline。A trigger that doesn't pick its moment trades noise for coverage. Pick the right moment, and you trade for a real baseline.
02 為什麼 AI review 結果走 PR comment，不直接改 code？why route AI review through a PR comment instead of editing code directly?

Review 跟 fix 是兩件事。AI 直接改 code 等於把人類踢出 loop——一旦判斷錯，錯誤會 cascade 進後續 commit、進 main、進 prod。改成只貼 comment、由人類過濾，AI 是「建議者」而不是「決策者」，trust boundary 永遠停在「貼字」這一層。Review and fix are two different acts. Letting AI edit code kicks the human out of the loop — once it gets a call wrong, the error cascades into the next commit, into main, into prod. Posting comments only and letting humans filter keeps AI as the suggester, not the decider; the trust boundary stops at "writing text".

AI 改 code 是把方向盤交出去；AI 貼 comment 是遞便利貼。場景該選哪個，看誰承擔錯的後果。AI editing code is handing over the steering wheel. AI posting comments is handing over a sticky note. Which one fits depends on who eats the cost of being wrong.
03 為什麼接受 AI review 噪音率高？why accept a high noise rate on AI review?

Baseline review 的價值不在每筆 finding 都對，是在「確保所有 PR 都至少被 review 一次」。沒這條 routine 之前，忙的 PR 沒人 review 就 merge 了；現在保證有 baseline，真人 review 還是要做、但底線守住了。雜訊是過濾掉的，沒 review 過的 PR 是補不回來的。The value of baseline review isn't that every finding is correct — it's that every PR gets reviewed at least once. Before this routine, busy PRs got merged unreviewed; now a baseline is guaranteed. Human review still happens, but the floor is held. Noise can be filtered out; PRs that were never reviewed can't be recovered.

完美 review 一筆都沒有，比有噪音的 review 守住整個 codebase 更糟。Zero perfect reviews is worse than noisy reviews holding the whole codebase.

AI baseline 抓得到的四類問題four classes of issues the AI baseline catches

🔒

Security smells

Hardcoded credential、SQL injection 風險、unsafe deserialization、LLM trust boundary 破口。模式類問題，pattern 比上下文重要——剛好是 LLM 強項。Hardcoded credentials, SQL injection risks, unsafe deserialization, LLM trust boundary leaks. Pattern-matching beats deep context here — which is exactly where LLMs shine.

🐛

Logic bugs

Off-by-one、null check 漏掉、async race condition、conditional side effect。剛寫完 code 的人最看不出來——剛好需要一雙「沒參與寫」的眼睛。Off-by-one, missing null checks, async race conditions, conditional side effects. The author who just wrote the code is the worst at seeing them — which is exactly where a fresh pair of eyes pays off.

🎨

Design issues

Single-responsibility 違反、可讀性差、過度抽象、duplication。Review 不一定對，但提示讓 dev 重新看一遍自己的設計，價值就在了。Single-responsibility violations, poor readability, over-abstraction, duplication. The review isn't always right, but the prompt makes the dev look at their own design again — that's where the value lands.

📋

Convention drift

Naming、folder structure、跟 repo 既有模式不一致。新人最容易踩、老人最容易忽略——AI 對 codebase pattern 反而沒有 bias。Naming, folder structure, drift from the repo's established patterns. New hires step on it, veterans gloss over it — AI has no bias either way against the codebase patterns.
