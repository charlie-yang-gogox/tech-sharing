WHY

為什麼要兩道？Why two fuses?

三個關鍵設計決策three design decisions
01 為什麼 spec-lint 是純 grep，不用 LLM？Why is spec-lint pure grep, no LLM?

Deterministic check 重跑結果永遠一樣，誤判率為 0；LLM-driven check 每次跑可能不同，會讓 lint 變成 unreliable 的噪音來源。9 個 check 都是純結構性檢查（label format、id 引用、文件之間的 cite），grep / awk / wc 足夠。Deterministic checks always agree across reruns and have a zero false-positive rate; LLM-driven checks shift every run, which turns lint into an unreliable noise generator. All 9 checks are structural (label format, id references, cross-file citations) — grep / awk / wc is enough.

需要 LLM 才判斷得出來的東西，本來就該是 /spec-review 的工作。Anything that needs an LLM to decide was always /spec-review's job.
02 為什麼 spec-review 不改 artifact，只判決定？Why does spec-review only render verdicts, never edit artifacts?

改 artifact 是 /port:revise 的事；/spec-review 是「人類最後一關」的純 gating role。把責任分清楚才能idempotent——人類 review 兩次同個 finding 應該得到同樣結論，不該每次都產生不同的 commit。決定全部留在 Linear comment 裡，下游 /dev:apply 讀 comment 當權威覆寫。Editing artifacts is /port:revise's job; /spec-review is the pure gating role — the human's last checkpoint. Splitting responsibilities cleanly is what makes it idempotent: reviewing the same finding twice should land on the same verdict, not spawn a different commit each time. Decisions stay inside the Linear comment, and downstream /dev:apply reads it as the authoritative override.

spec-review 是 gate，不是 editor。職責切乾淨才能重跑、才能信任。spec-review is a gate, not an editor. Clean separation is what makes it rerunnable and trustworthy.
03 為什麼 bidirectional citation 同時抓 omission + hallucination？Why does bidirectional citation catch omission and hallucination at once?

Forward direction：spec 提到的 FR-N 在 pm-notes 裡找得到嗎？抓「synthesis 漏寫」。Reverse direction：pm-notes 寫的 FR-N 在 spec 裡有被 cite 嗎？抓「synthesis 幻覺出本來沒有的 spec」。同一個 check 跑兩個方向，兩種錯都防得到。Forward direction: does every FR-N the spec mentions exist in pm-notes? Catches "synthesis dropped it". Reverse direction: is every FR-N from pm-notes cited in the spec? Catches "synthesis hallucinated a spec that was never requested". One check, two directions, both failure modes covered.

一個 labeled-ID 機制 × 兩個方向 = 漏寫跟幻覺一網打盡。One labeled-ID mechanism × two directions = omission and hallucination both nailed.

TAKEAWAY

記住這四件事Four things to remember

分享結束如果只能帶走幾句話if you only walk away with a few lines
  1. deterministic check 比 LLM check 可靠——重跑不變、誤判為零、執行成本接近 0，可以塞 CI、可以隨便跑。deterministic checks beat LLM checks — stable across reruns, zero false positives, near-zero cost; safe to bolt onto CI and run whenever.
  2. 機器抓得到的不該讓人類抓——9 個 lint check 攔下純結構錯誤，人類只看判斷題，不重工。do not make humans catch what the machine can — 9 lint checks block the structural errors, so humans only deal with judgment calls. No duplicated work.
  3. bidirectional citation 同時防漏寫 + 幻覺——一個 labeled-ID 機制跑兩個方向，覆蓋 omission 與 hallucination 兩種雙向錯誤。bidirectional citation blocks omission and hallucination at once — one labeled-ID mechanism, two directions, both failure modes covered.
  4. /spec-review 是純 Linear gate——不動 filesystem、不 commit、不 push，人類只負責 Confirm / Revise / Defer，決定全部留在 Linear comment。/spec-review is a pure Linear gate — no filesystem writes, no commits, no pushes. Humans only deliver Confirm / Revise / Defer, and every decision lives in the Linear comment.
